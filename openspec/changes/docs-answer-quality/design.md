# Design

## Context

Замер 6.3 после веса вида (README «Замер после веса вида»): ≈14 из 20, пять ложных отказов
(`data-export`, `asset-revaluation`, `icon-sync` ×2, `currency-pairs`) при ранге спеки 1 по
вектору. Модель чата — `gemma-4-e4b` без рассуждения (`LLM_REASONING_CHAT=none`), эмбеддинги —
`text-embedding-nomic-embed-text-v1.5`. Один GPU GTX 1070 8 ГБ: модели ≤ 8B Q4, одновременно
в памяти чат и эмбеддинги. Набор вопросов прошлых замеров нигде не хранится, поэтому сравнивать
изменения нечем — это первая задача.

## Goals / Non-Goals

**Goals:**
- ≥ 16 из 20 верных на сохранённом наборе, ложные отказы — отдельной строкой.
- Каждое изменение промпта/параметров проверяется на одном и том же наборе.

**Non-Goals:**
- Новые эндпоинты, смена контракта `/api/docs/ask`, правка области доступа.
- Внешние LLM (облачные): стек остаётся на LM Studio локально.

## Decisions

**D1. Сначала набор и скрипт, потом правки.** Набор — файл вопросов (`tests/quality/
questions.json`: вопрос, платформа токена, ожидаемый `repo/capability` или «ответа нет»),
скрипт `scripts/quality.sh` ходит в `wallet-docs` на стенде. Альтернатива «оценивать вручную
каждый раз» отвергнута: прошлые два замера на разных наборах сопоставимы лишь грубо.

**D2. «Не по теме» до LLM — только при надёжном сигнале, иначе не вводим.** Расстояния
пересекаются (0,163–0,253 и 0,231–0,293), порог по первому чанку не годится. Проверяются
сигналы на размеченном наборе (вопросы по теме из D1 + 8 нейтральных): расстояние первого
чанка вместе с `ts_rank` первого полнотекстового кандидата, разрыв между 1-м и 2-м
кандидатом. Правило вводится, только если оно не отсекает ни одного вопроса по теме на
наборе; иначе вывод пишется сюда, а отказ остаётся за промптом (так и записано в спеке).
Ложный отказ по теме хуже лишнего вызова LLM.

**D3. Порядок экспериментов — от дешёвого к дорогому, по одному за замер.** (1) промпт:
отказ только «если во фрагментах нет ничего по теме вопроса», частичный ответ допустим,
сначала самое релевантное; (2) оформление фрагментов (короче служебная обвязка, заголовок
раздела в начале); (3) `kTop` 8 → 6 или 10; (4) `LLM_REASONING_CHAT` ≠ `none` — дороже по
времени, проверить p95; (5) другая чат-модель ≤ 8B Q4. Смена модели эмбеддингов — последний
шаг: поиск не виноват (ранг 1), а перезаливка индекса и подбор порога дороги.

**D4. Время ответа не должно вырасти заметно.** По задаче 3.4 `docs-tool` ответ укладывается
в таймаут MCP; рассуждение модели и 10 фрагментов проверяются замером p95 на том же наборе.

## Risks / Trade-offs

- **Подгонка под набор из 20.** Промпт можно подогнать под известные вопросы. Смягчение:
  часть набора (6 вопросов) откладывается как проверочная и не используется при подборе.
- **Модель ≤ 8B может не дотянуть.** Тогда результат записывается как предел железа, change
  закрывается с фактическим числом, решение о более сильной модели — владельцу.
- **Вес «ложный отказ против выдуманного ответа».** Ослабление отказа повышает риск ответа
  не по фрагментам; проверяется вопросами «ответа нет» из набора и обязательными `[n]`.
